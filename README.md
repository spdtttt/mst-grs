# NEW-MST-GRS

ระบบแก้ไขผลการเรียนคงค้าง ภาษาไทย โทนม่วง ใช้ Next.js App Router, TypeScript และ Supabase PostgreSQL/Auth

## เริ่มต้น

1. ใช้ Node.js 22 ขึ้นไป แล้ว `npm install`
2. คัดลอก `.env.example` เป็น `.env.local` ใส่ Supabase URL, Publishable key และ `LOGIN_HMAC_SECRET` สุ่มอย่างน้อย 32 ตัวอักษร (ห้ามเปลี่ยนหลังสร้างบัญชีโดยไม่มีแผนย้ายบัญชี) สำหรับ Web Push ให้สร้าง VAPID key หนึ่งชุดด้วย `npx web-push generate-vapid-keys --json` แล้วตั้งค่าตามชื่อในไฟล์ตัวอย่าง
3. เปิด Supabase SQL Editor แล้วรันไฟล์ใน `supabase/migrations` ตามลำดับเลข (`001`–`013`, `016`–`028`) หนึ่งครั้ง โดยรัน `024` และ `025` แยกคำสั่งเพื่อให้ enum บันทึกค่า Admin ก่อน ระบบเริ่มต้นเป็นสถานะปิด
4. ปิด Allow new users to sign up ใน Supabase Authentication เพื่อให้สร้างบัญชีผ่านเครื่องมือของโรงเรียนเท่านั้น
5. เตรียมบัญชีตามหัวข้อด้านล่างและสร้างบัญชี Admin ก่อน
6. `npm run dev` แล้วเปิด http://127.0.0.1:3000 เข้าบัญชี Admin แล้วเลือกเมนูตั้งค่าเวลาเปิด–ปิดระบบ
7. `npm run build` และ `npm start` สำหรับ production บน Node.js หรือ deploy ด้วยผู้ให้บริการที่รองรับ Next.js เช่น Vercel ตั้ง environment variables บน server และใช้ HTTPS

ไฟล์ environment จริงถูกละเว้นจาก Git ห้าม commit หรือส่ง `LOGIN_HMAC_SECRET`, `SUPABASE_SERVICE_ROLE_KEY` และ `VAPID_PRIVATE_KEY`

## อัปเกรดจากระบบ 4 บทบาท

รัน `supabase/migrations/004_academic_schedule.sql` ใน Supabase SQL Editor หลังจากติดตั้ง 001–003 แล้ว จากนั้นใช้บัญชีฝ่ายวิชาการเดิมตั้งเวลาได้ทันที สคริปต์ลบบัญชี admin เดิมออกจาก profiles และ Supabase Auth พร้อมนำค่า admin ออกจาก enum ของฐานข้อมูล เก็บ audit log เดิมโดยตั้ง actor_id ของบัญชีที่ลบเป็น null หากมีผลการเรียนหรือไฟล์แนบอ้างถึงบัญชีนั้น สคริปต์จะหยุดและย้อนกลับทั้ง transaction เพื่อไม่ลบข้อมูลเหล่านั้น

หลังจาก 004 ให้รัน `supabase/migrations/005_manager_role.sql` เพื่อเพิ่มบทบาท manager และ `supabase/migrations/006_manager_dashboard_stats.sql` เพื่อเปิดสถิติแบบสรุป จากนั้นสร้างบัญชีจาก `data/accounts/accounts-manager.csv` โดยตรวจด้วย `npm run accounts -- data/accounts/accounts-manager.csv` และสร้างจริงด้วย `npm run accounts -- data/accounts/accounts-manager.csv --apply` ไฟล์นี้คัดเฉพาะ manager จากแถว 5 ของ `data/accounts/Book1.csv` อยู่ในเครื่องและถูกละเว้นจาก Git; เก็บรหัสผ่านอย่างปลอดภัยก่อนลบไฟล์ บัญชี manager ใช้หน้า `/dashboard/manager` หน้าเดียว โดยสลับ Dashboard สถิติ รายการที่ยังไม่เสร็จสิ้น และรายการที่เสร็จสิ้นแล้วภายในหน้าโดยไม่รีโหลดเว็บ

## บัญชีและสิทธิ์ Admin

รัน `024_admin_role.sql` แล้วรัน `025_admin_operations.sql` แยกครั้งกันใน Supabase SQL Editor ก่อน deploy โค้ดนี้ Migration แรกเพิ่ม role `admin` ส่วน migration ถัดไปย้ายสิทธิ์ `import_grades` และ `update_schedule` จากฝ่ายวิชาการไปยัง Admin โดยยังตรวจบทบาทและช่วงเวลาเปิดระบบในฐานข้อมูล ฝ่ายวิชาการยังตรวจและอนุมัติผลการเรียนได้ แต่จะนำเข้าข้อมูลหรือตั้งเวลาไม่ได้

สร้างไฟล์ CSV สำหรับบัญชี Admin บนเครื่องของผู้ดูแลโดยใช้คอลัมน์ `role,identifier,citizen_id,full_name,classroom,password` กำหนด `role` เป็น `admin`, ตั้งชื่อผู้ใช้ใน `identifier` และรหัสผ่านเฉพาะใน `password` โดยปล่อย `citizen_id` และ `classroom` ว่าง จากนั้นตรวจด้วย `npm run accounts -- path/to/admin.csv` และสร้างจริงด้วย `npm run accounts -- path/to/admin.csv --apply` อย่า commit ไฟล์บัญชีหรือรหัสผ่าน

Admin เข้า `/dashboard/admin` เพื่อจัดการรายชื่อนักเรียน นำเข้าผลการเรียน และตั้งวันที่เปิด–ปิดระบบ ส่วนผู้บริหารเข้า `/dashboard/manager` และนักเรียน ครู ฝ่ายวิชาการเข้า `/dashboard` ระบบตรวจบทบาทซ้ำที่หน้า Server Action และฟังก์ชันฐานข้อมูล

### รายชื่อนักเรียนของ Admin

รัน `027_admin_students.sql` หลัง migration `026` แล้วรัน `028_student_import_speed_cancel.sql` เพื่อเพิ่มการยกเลิกนำเข้าและเรียงชั้น/ห้อง ตั้ง `SUPABASE_SERVICE_ROLE_KEY` บนเซิร์ฟเวอร์ (ห้ามใช้ชื่อขึ้นต้น `NEXT_PUBLIC_`) และใช้ `LOGIN_HMAC_SECRET` เดียวกับบัญชีเดิม เมนู **รายชื่อนักเรียน** อยู่ในหน้า Admin หรือเปิด `/dashboard/admin?view=students` ได้โดยตรง จัดการบัญชีได้ทั้งช่วงเปิดและปิดรับคำร้อง

- ตารางแสดงรหัสนักเรียน ชื่อรวม ชั้น/ห้อง และเลขที่ ของนักเรียนทุกคนจาก `profiles` พร้อมค้นหาชื่อ/รหัส กรองระดับชั้น ม.1–ม.6 และแบ่งหน้าละ 50 คน เรียงตามระดับชั้นและห้องแบบตัวเลข เช่น ม.1/2 ก่อน ม.1/10 แล้วเรียงเลขที่ พรีวิวใช้ลำดับเดียวกัน บัญชีเก่าที่ไม่มีเลขที่จะแสดง `—`
- เพิ่มผ่านฟอร์ม หรือไฟล์ `.xlsx` โดยอ่านครบทุกชีท รวม ม.1–ม.6 แต่ละชีทใช้คอลัมน์ `เลขประจำตัวประชาชน`, `รหัสนักเรียน`, `คำนำหน้าชื่อ`, `ชื่อ`, `นามสกุล`, `ชั้น/ห้อง`, `เลขที่` ดาวน์โหลดแม่แบบหกชีทจากหน้านี้ได้
- รวมชื่อเป็น `คำนำหน้าชื่อ+ชื่อ นามสกุล` เช่น `เด็กชายศุภพล แดงประทีป` ลบ `-` จากเลขบัตร ตรวจเลขบัตร 13 หลัก รหัสนักเรียน 5–10 หลัก และชั้น/ห้อง เช่น `ม.4/9` เก็บสองคอลัมน์รหัสเป็นข้อความใน Excel เพื่อรักษาศูนย์นำหน้า
- บัญชีใหม่สร้าง Supabase Auth ก่อน จากนั้นบันทึก `profiles` เป็น `student` พร้อมชื่อแยกและชื่อรวม ชั้น/ห้อง เลขที่ และ `citizen_id_encrypted` นักเรียนเข้าสู่ระบบด้วยรหัสนักเรียนและเลขบัตร โดยใช้ HMAC ตามระบบเดิม เลขบัตรถูกเข้ารหัส AES-256-GCM บนเซิร์ฟเวอร์ด้วย key ที่แยกการใช้งานจาก `LOGIN_HMAC_SECRET` และผูกกับรหัสนักเรียน ไม่เก็บเลขบัตรเป็นข้อความ ไม่ส่งข้อมูลเข้ารหัสกลับในรายชื่อ และไม่แสดงในตารางหรือพรีวิว
- รหัสนักเรียนที่มีอยู่แล้วตรวจ Auth ให้ตรงบัญชีก่อนอัปเดตเฉพาะข้อมูลรายชื่อ เก็บ ID และรหัสผ่านเดิม ไม่สร้าง Auth ซ้ำ และไม่แก้ไขรายการผลการเรียนที่มีอยู่
- ไฟล์ที่มีข้อมูลผิดหรือรหัสซ้ำในชีทเดียวกันหรือข้ามชีทจะยังนำเข้าไม่ได้ ตรวจทั้งหมดก่อนสร้างบัญชีจริง รองรับชีทละ 2,000 แถว ไม่มีเพดานขนาดไฟล์ในแอป
- แสดง Popup ระหว่างอ่านไฟล์และสร้างบัญชี พร้อมชีทที่กำลังตรวจ จำนวนรายการที่ตรวจ/บันทึกแล้ว และเปอร์เซ็นต์ เมื่อเสร็จจะปิด Popup และแสดงผลลัพธ์
- ส่งข้อมูลชุดละ 50 คน ค้นหาโปรไฟล์เดิมครั้งเดียวต่อชุด แล้วสร้างหรืออัปเดตพร้อมกันสูงสุด 5 คน แสดงผลเพิ่มใหม่/อัปเดต/ไม่สำเร็จ แถวที่บันทึกสำเร็จแล้วคงอยู่แม้แถวอื่นผิดพลาด แถวที่ล้มเหลวยังคงอยู่ในพรีวิวสำหรับตรวจและลองใหม่ จึงไม่ใช่ transaction เดียวทั้งไฟล์
- ปุ่ม **Cancel** หรือ Escape ใน Popup หยุดอ่านไฟล์หรือหยุดเริ่มบัญชีใหม่ทันที เมื่อเซิร์ฟเวอร์รับคำสั่งแล้วจะให้เฉพาะงานที่เริ่มอยู่สูงสุด 5 คนจบก่อนปิด Popup เก็บรายการที่บันทึกแล้ว และเหลือรายการที่ยังไม่ได้ทำในพรีวิว หากส่งคำสั่งยกเลิกไม่สำเร็จ จะหยุดส่งชุดใหม่และรอชุดปัจจุบันจบ พร้อมแสดงข้อความและปุ่มลองยกเลิกอีกครั้ง
- คำสั่งยกเลิกส่งผ่าน Route Handler แยกจาก Server Action รอบนำเข้าผูกกับ Admin ผู้เริ่มรอบ มีอายุ 24 ชั่วโมง และทำได้ครั้งละหนึ่งชุดต่อรอบ ตารางควบคุมเก็บเฉพาะสถานะและรหัสรอบ ไม่เก็บข้อมูลนักเรียนหรือรหัสผ่าน
- หากบันทึกโปรไฟล์ล้มเหลว จะตรวจว่า transaction บันทึกสำเร็จแล้วหรือไม่ก่อนย้อนกลับ Auth ที่เพิ่งสร้าง หากยืนยันหรือย้อนกลับไม่ได้ จะแจ้งให้ตรวจ Supabase Auth และ profiles ก่อนลองใหม่ การสร้าง/แก้ไขโปรไฟล์และ audit log บันทึกใน transaction เดียว
- ทุก Server Action และ RPC ตรวจ Admin ซ้ำ service key อยู่บนเซิร์ฟเวอร์เท่านั้น สิทธิ์อ่าน/เขียน `profiles` โดยตรงของบทบาทอื่นยังเหมือนเดิม

## ประวัติการแก้ไขเมื่อปิดรอบ

หลัง migrations 001–013 ให้รัน `supabase/migrations/016_grade_record_history.sql` และ `supabase/migrations/017_history_cron.sql` ตามลำดับ ด้วยบัญชี postgres ใน Supabase SQL Editor ก่อน deploy โค้ดนี้ ต้องเปิดใช้ extension `pg_cron` ได้ (Supabase Cron) หากเวลาปิดเดิมผ่านไปแล้ว migration 016 จะย้ายรายการสำเร็จที่มีอยู่ทันที

- ตาราง `grade_record_history` เก็บข้อมูลผลการเรียนเดิมครบทุกช่อง พร้อม `archived_at` (เวลาย้ายจริง) และ `archived_closes_at` (เวลาปิดรอบ)
- Job `mst-grs-archive-completed` เรียก `archive_completed_grade_records()` ทุก 30 วินาที เมื่อถึง `site_schedule.closes_at` จะคัดลอกเฉพาะสถานะ `completed` เข้าประวัติแล้วลบจาก `grade_records` ภายใน transaction เดียว ไม่ต้องมีผู้เปิดเว็บไซต์อยู่ การย้ายอาจช้ากว่าเวลาปิดประมาณหนึ่งรอบการตรวจหรือมากกว่านั้นหากฐานข้อมูลติดล็อก/ไม่พร้อมให้บริการ และจะลองใหม่ในการรันถัดไป
- ภาระงาน ไฟล์แนบ และ audit log ย้ายความสัมพันธ์จาก `record_id` ไป `archived_record_id` โดยเก็บรหัสรายการ/ภาระงาน/ไฟล์เดิมไว้ ไม่ลบไฟล์ใน Storage
- **ประวัติเปิดอ่านได้ตลอดเวลาหลังเข้าสู่ระบบ** ไม่ขึ้นกับช่วงเวลาเปิด–ปิด นักเรียนเห็นของตัวเอง ครูรวมถึงครูร่วมสอนเห็นวิชาที่ตนสอน ฝ่ายวิชาการเห็นทั้งหมด โดยบังคับสิทธิ์ด้วย RLS ของ Supabase
- หน้าประวัติอ่านจากตารางใหม่เท่านั้น รายการที่เพิ่ง `completed` แต่รอบยังไม่ปิดยังอยู่ใน `grade_records` และยังไม่แสดงในประวัติ
- งานที่ยังไม่สำเร็จอยู่ใน `grade_records` ต่อไป การนำเข้าแถวเดิมที่เคยเก็บในประวัติแล้วจะนับเป็นรายการข้าม เพื่อไม่ให้เกิดงานซ้ำ
- การเปิดรอบใหม่หลังหมดเวลาจะเก็บรายการสำเร็จของรอบเดิมก่อน แม้ cron ยังไม่ถึงรอบรัน ส่วนการเลื่อนเวลาปิดก่อนถึงกำหนดเดิมจะใช้เวลาใหม่
- เมนูประวัติมีค้นหา ตัวกรองปี/ภาคเรียนของวิชา ส่งออก CSV และลิงก์เปิดภาระงาน/ไฟล์แนบย้อนหลัง ดูตรงได้ที่ `/dashboard?view=history`
- ตรวจสถานะ job และการรันได้ใน Supabase → Integrations → Cron โดยใช้ชื่อ job ข้างต้น ฟังก์ชันย้ายข้อมูลไม่เปิดสิทธิ์เรียกจาก browser

เอกสารอ้างอิง: [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart)

## วันที่เปิด–ปิดระบบ

### เริ่มใหม่เมื่อปิดรอบ

หลังติดตั้ง migrations ถึง `020` ให้รัน `supabase/migrations/021_reset_unfinished_on_close.sql`
ด้วยบัญชี postgres ใน Supabase SQL Editor โดยต้องมี cron จาก migration `017` แล้ว
เมื่อพ้นวันปิดตามเวลาไทย งานอัตโนมัติจะดำเนินการภายในรอบตรวจทุก 30 วินาที แม้ไม่มีผู้เปิดเว็บ:

- รายการ `completed` ย้ายเข้าประวัติการแก้ไขสำเร็จตามเดิม
- รายการที่ยังไม่สำเร็จทุกสถานะ รวม `teacher_approved` กลับเป็น `pending`
  ล้างรายละเอียดงาน กำหนดส่ง วันยื่นคำร้อง วันรับงาน ข้อมูลอนุมัติ และเกรดใหม่
  โดยคงรายวิชา ผลการเรียนเดิม ปีการศึกษา และภาคเรียนของรายการเดิมไว้
- เก็บข้อมูลก่อนรีเซ็ทใน `grade_reset_history` และย้ายการอ้างอิงภาระงาน/ไฟล์เดิมไปที่รายการนี้
  รอบใหม่จึงเริ่มมอบหมายงานรอบที่ 1 ได้ โดยไม่ลบไฟล์เดิมออกจาก Storage
  ข้อมูลนี้ยังไม่มีหน้าจอดูโดยเฉพาะ และไม่ปนกับประวัติรายการที่แก้ไขสำเร็จ
- บันทึกวันปิดที่ประมวลผลแล้ว ป้องกัน cron รีเซ็ทซ้ำ และรีเซ็ทให้ด้วยหากเปิดรอบใหม่ก่อน cron ทำงาน

หากวันปิดปัจจุบันผ่านไปแล้ว migration `021` จะประมวลผลรอบนั้นทันทีเมื่อรัน

### แก้ไขผลการเรียนใหม่ระหว่างรอบ

รัน `supabase/migrations/022_grade_corrections.sql` และ `023_allow_all_new_grades.sql`
ตามลำดับ หลัง `021` ก่อน deploy แอปเวอร์ชันนี้
ครูประจำวิชาแก้ผลการเรียนใหม่ได้ในหน้า “คำร้องของนักเรียน” เมื่อรายการยังอยู่ในรอบปัจจุบัน
และมีสถานะ “รอฝ่ายวิชาการอนุมัติ” หรือ “แก้ไขสำเร็จ” เท่านั้น
ทุกครั้งที่แก้ ระบบเก็บค่าเดิม ค่าใหม่ ชื่อครู และเวลาไว้ใน `grade_corrections`
ประวัติการแก้ยังอ่านได้หลังรายการย้ายเข้าหน้าประวัติ แต่แก้รายการนั้นไม่ได้แล้ว
ผลการเรียนใหม่เลือกเป็น `0`, `ร` หรือ `มผ` ได้ ทั้งตอนครูอนุมัติครั้งแรกและตอนแก้ไขภายหลัง

### การเลือกวันที่

รัน `supabase/migrations/020_date_only_schedule.sql` ก่อน deploy การตั้งค่าแบบเลือกวันที่
ระบบเปิดตั้งแต่เริ่มวันเปิดจนสิ้นสุดวันปิดตามเวลาไทย และเลือกเปิด–ปิดวันเดียวกันได้
ฐานข้อมูลเก็บขอบเขตปิดเป็นเที่ยงคืนของวันถัดไป เพื่อให้ cron ย้ายรายการเข้าประวัติหลังจบวันปิด
Migration ปรับเวลาเดิมเป็นช่วงเต็มวัน โดยไม่ย้ายรายการเข้าประวัติระหว่างการแปลงค่า

## การอัปโหลดไฟล์มอบหมายงาน

ก่อนใช้การอัปโหลดตรงเข้า Storage ให้รัน `supabase/migrations/019_direct_assignment_uploads.sql`
ใน Supabase SQL Editor แล้ว deploy แอปเวอร์ชันใหม่ Migration นี้ยกเลิกเพดานขนาดและจำนวนไฟล์ของแอป
เปลี่ยน `size_bytes` เป็น `bigint` และตรวจขนาดกับชนิดไฟล์จาก Storage จริงก่อนบันทึกงาน
ข้อมูลและไฟล์เดิมยังอยู่ครบ

ไฟล์ส่งจากเบราว์เซอร์ไป Supabase Storage ด้วย signed token และ TUS ซึ่งแบ่งส่งเป็นส่วน ๆ
และลองส่งต่อเมื่อเครือข่ายสะดุด ส่วน Server Actions รับเฉพาะข้อความกับข้อมูลอ้างอิงไฟล์
จึงไม่ส่งไฟล์ขนาดใหญ่ผ่าน Vercel Functions

แอปไม่กำหนดเพดานขนาดไฟล์ แต่ยังขึ้นกับ Global file size limit ใน Supabase Storage Settings
และแพ็กเกจของโครงการ หาก Storage ปฏิเสธเพราะขนาดเกิน ให้ตรวจการตั้งค่านี้
ดู [ข้อจำกัด Supabase Storage](https://supabase.com/docs/guides/storage/uploads/file-limits)

## บัญชีและวิธีเข้าสู่ระบบ

| บทบาท               | ข้อมูลเข้าสู่ระบบ                                  |
| ------------------- | -------------------------------------------------- |
| นักเรียน            | เลขประจำตัวนักเรียน + เลขบัตรประชาชน 13 หลัก       |
| ครู                 | เลขบัตรประชาชน 13 หลักอย่างเดียว ตามข้อกำหนดผู้ใช้ |
| ฝ่ายวิชาการ         | เลขบัตรประชาชน 13 หลักอย่างเดียว                   |
| ผู้บริหาร (manager) | ชื่อผู้ใช้ + รหัสผ่านอย่างน้อย 6 ตัวอักษร          |
| ผู้ดูแลระบบ (admin) | ชื่อผู้ใช้ + รหัสผ่านอย่างน้อย 6 ตัวอักษร          |

เลขบัตรประชาชนเป็นข้อมูลระบุตัวตน ไม่ใช่ความลับที่ปลอดภัย ผู้ที่ทราบเลขบัตรของครูหรือฝ่ายวิชาการสามารถเข้าสวมสิทธิ์ได้ การจำกัดความถี่ไม่ได้แก้ปัญหานี้ แนะนำเพิ่ม OTP หรือรหัสผ่านก่อนใช้งานกับข้อมูลจริง หากต้องรักษาวิธีเข้าสู่ระบบนี้ควรจำกัดการเข้าถึงเครือข่ายโรงเรียนด้วย reverse proxy ที่เชื่อถือได้

ระบบไม่เก็บเลขบัตรดิบใน profiles หรืออีเมล ใช้ HMAC พร้อม secret ฝั่ง server สร้าง auth identity และ credential สำหรับนักเรียน ครู และฝ่ายวิชาการ ส่วน manager และ admin ใช้รหัสผ่านที่ตั้งไว้ Supabase Auth เก็บ hash รหัสผ่าน ไม่ใช่การทำให้การเข้าสู่ระบบด้วยเลขบัตรอย่างเดียวปลอดภัยเท่ารหัสผ่าน การจำกัดการพยายามเข้าสู่ระบบคือ 10 ครั้งต่อบัญชีต่อ 15 นาที (รวมครั้งสำเร็จ) และใช้ rate limit ของ Supabase เพิ่มเติม

สร้าง CSV UTF-8 ในเครื่องที่เชื่อถือได้ โดยมีหัว:

```csv
role,identifier,citizen_id,full_name,classroom,password
```

- student: identifier = เลขนักเรียน, citizen_id = เลขบัตร, classroom = ห้อง
- teacher: identifier = เลขบัตร, citizen_id เว้นว่าง, full_name ต้องตรงกับชื่อครูคนใดคนหนึ่งในคอลัมน์ครูผู้สอน
- academic: identifier = เลขบัตร, citizen_id/classroom เว้นว่าง
- manager: identifier = ชื่อผู้ใช้ภาษาอังกฤษ 3–40 ตัวอักษร, password อย่างน้อย 6 ตัวอักษร; citizen_id/classroom เว้นว่าง แนะนำให้เปลี่ยนเป็นรหัสผ่านยาวและไม่ซ้ำก่อนใช้งานจริง
- admin: identifier = ชื่อผู้ใช้ภาษาอังกฤษ 3–40 ตัวอักษร, password อย่างน้อย 6 ตัวอักษรโดยไม่มีช่องว่างนำหน้าหรือต่อท้าย; citizen_id/classroom เว้นว่าง ใช้รหัสผ่านยาวและไม่ซ้ำ

ตั้ง `SUPABASE_SERVICE_ROLE_KEY` ใน `.env.local` บนเครื่องผู้ดูแล **ห้ามส่งในแชต ห้ามใช้ NEXT_PUBLIC\_ ห้าม commit** ตรวจข้อมูลก่อนด้วย `npm run accounts -- accounts.csv` แล้วสร้างจริงด้วย `npm run accounts -- accounts.csv --apply` เครื่องมือไม่พิมพ์เลขบัตรหรือรหัสผ่าน ไม่เขียนทับบัญชีเดิม และ rollback บัญชี Auth ถ้าสร้าง profile ไม่สำเร็จ เก็บหรือลบไฟล์บัญชีตามนโยบายข้อมูลของโรงเรียน เก็บ secret ให้สำรองและจำกัดผู้เข้าถึง

หากต้องตรวจว่ารหัสผ่านใน CSV ปัจจุบันเข้าใช้งานได้ ให้รัน `npm run accounts -- path/to/admin.csv --verify-admin-login` หากต้องรีเซ็ตรหัสผ่าน Admin เดิม ให้ทำ CSV ที่มีเฉพาะบัญชี Admin หนึ่งแถวและรหัสผ่านใหม่อย่างน้อย 6 ตัวอักษร ตรวจด้วย `npm run accounts -- path/to/admin.csv --reset-admin-password` แล้วจึงรัน `npm run accounts -- path/to/admin.csv --reset-admin-password --apply` คำสั่งนี้ตรวจว่าชื่อผู้ใช้ตรงกับ Auth และ profile เดิมก่อนเปลี่ยนรหัสผ่าน โดยไม่สร้างบัญชีซ้ำ

## กระบวนการ

`pending (0%) → requested (25%) → assigned (50%) → submitted (75%) → teacher_approved (75%) → completed (100%)`

- นักเรียนเห็นเฉพาะของตน ยื่นคำร้องและเปิดหน้ารายละเอียดงานเพื่ออ่านคำสั่งหรือดาวน์โหลดไฟล์แนบ ส่งงานให้ครูภายนอกระบบ
- ตัวกรอง “สถานะทั้งหมด” ของนักเรียนและครูแสดงทุกรายการที่ยังไม่เข้าประวัติ รวมสถานะยังไม่ยื่นคำร้องและแก้ไขสำเร็จ ครูเปิดหน้ามอบหมายงาน ระบุกำหนดส่ง และแนบไฟล์ตรงเข้า Supabase Storage โดยแอปไม่จำกัดจำนวนหรือขนาดไฟล์ (ยังขึ้นกับเพดาน Storage ของโครงการ) จากนั้นรับงานและอนุมัติพร้อมระบุเกรดใหม่ ส่งออกได้ทุกสถานะที่ยังไม่เข้าประวัติ หากรายวิชามีครูหลายคน ทุกคนจะเห็นรายการเดียวกันและดำเนินการตามสถานะปัจจุบันได้
- ครูเปิด Web Push ได้จากแถบด้านข้าง เมื่อมีคำร้องใหม่ระบบส่งข้อความทั่วไปที่ไม่มีชื่อหรือผลการเรียน กดแล้วเปิดรายการนั้น หาก session หมดอายุจะเข้าสู่ระบบก่อนแล้วกลับมายังรายการเดิม การ Logout ไม่ปิดการแจ้งเตือนเพื่อให้ครูยังได้รับข้อความหลัง session หมดอายุ หากเป็นเครื่องส่วนกลางให้กด "ปิดบนอุปกรณ์นี้" ก่อน Logout
- ฝ่ายวิชาการเห็นรายการครูอนุมัติแล้ว อนุมัติสุดท้าย และส่งออกเฉพาะที่อนุมัติครบแล้ว
- Admin นำเข้าไฟล์เมื่อระบบเปิด และตั้งวันที่เปิด–ปิดได้แม้ระบบปิดอยู่ การดูและแก้ไขรายการปัจจุบันต้องอยู่ในช่วงเวลาให้บริการ ส่วนประวัติการแก้ไขเปิดอ่านได้ตลอดเวลา

- ผู้บริหารเห็น Dashboard สถิติจากข้อมูลจริง โดยการ์ดนับรายการรายวิชา ส่วนกราฟนับนักเรียนแต่ละคนเพียงครั้งเดียวตามระดับชั้นล่าสุด นักเรียนที่ยังมีรายวิชาไม่เสร็จอยู่ในกลุ่มยังไม่เรียบร้อย และดูรายชื่อพร้อมกรองระดับชั้น ปี/ภาคเรียนล่าสุด และเปิดรายละเอียดรายวิชาได้
- เวลาเปิดรวมจุดเริ่มต้น เวลาปิดไม่รวมจุดสิ้นสุด ประเมินจากเวลาฐานข้อมูล บันทึก timestamptz และแสดง Asia/Bangkok

## นำเข้าและส่งออก

รองรับ `.xlsx`, `.csv`, `.tsv` UTF-8 โดยไม่กำหนดเพดานขนาดไฟล์ในแอป แต่จำกัด 2,000 แถวต่อครั้ง เบราว์เซอร์ต้องอ่านไฟล์ทั้งไฟล์ก่อนตรวจจำนวนแถว อ่านแผ่นงานแรกของ XLSX; ไฟล์ `.xls` ต้อง Save As `.xlsx` ก่อน บันทึกเฉพาะ 11 คอลัมน์: รหัสวิชา, ชื่อวิชา, หน่วยกิต, ชั้น/ห้อง, ครูผู้สอน, เลขประจำตัว, ชื่อ-นามสกุล, เลขที่, ปีการศึกษา, ภาคเรียนที่, ผลการเรียน

รองรับผลค้าง 0, ร, มส, มผ ต้องเตรียมบัญชีนักเรียนและครูก่อน คอลัมน์ครูผู้สอนรับชื่อเดียวหรือหลายชื่อ เช่น `1.นางสาวนวิยา หมื่นหนู, 2.นางสาววรัญรัตน์ เพชรชำนาญ` ระบบตัดเลขกำกับแล้วเก็บ `teacher_name` และ `teacher_id` เป็น array ตามลำดับ ชื่อครูทุกคนต้องตรงกับบัญชีและไม่ซ้ำ หากมี `-ครูที่ปรึกษาชุมนุม -` ให้แก้เป็นชื่อครูจริงก่อนนำเข้า ตรวจชื่อนักเรียนตรงบัญชีด้วย เลขนักเรียนควรเป็นข้อความเพื่อรักษาศูนย์นำหน้าใน Excel นำเข้าแบบ atomic: ผิดหนึ่งแถวจะไม่บันทึกทั้งชุด ไฟล์แม่แบบดาวน์โหลดจากหน้า Import

### การเขียนทับรายการนำเข้าซ้ำ

ระบบที่ติดตั้งถึง migration `025` ต้องรัน `026_overwrite_grade_imports.sql` ใน Supabase SQL Editor ก่อนใช้โค้ดนี้ Server Action เรียก `import_grades_overwrite` เพื่อป้องกันฐานข้อมูลเวอร์ชันเดิมข้ามรายการซ้ำโดยเงียบ ๆ ส่วน RPC `import_grades` เดิมเรียกพฤติกรรมใหม่ด้วย

- ใช้เลขนักเรียน รหัสวิชา ปีการศึกษา และภาคเรียนทั้งสี่ค่าตรงกันเพื่อตรวจรายการซ้ำ
- เขียนทับเฉพาะรายการปัจจุบันทุกสถานะ รวมถึงแก้ไขสำเร็จที่ยังไม่เข้าประวัติ อัปเดตข้อมูลจากไฟล์ กลับเป็น `pending` และล้างคำร้อง งาน กำหนดส่ง เวลาดำเนินการ และผลการเรียนใหม่
- เก็บ ID และเวลาสร้างเดิม พร้อมสำเนาข้อมูลก่อนเขียนทับใน `grade_reset_history` (`reset_reason = 'import_overwrite'`) ย้ายงานและไฟล์เดิมไปอ้างอิงสำเนานี้ จึงไม่ถูกนำมาใช้เป็นความคืบหน้ารอบใหม่ ไฟล์ใน Storage และประวัติการแก้ไขผลการเรียนยังคงอยู่ภายใต้สิทธิ์เดิม
- รายการที่เข้าประวัติแล้วถูกข้าม ไม่เขียนทับหรือสร้างกลับมา รายการซ้ำภายในไฟล์เดียวกันยังเป็นข้อผิดพลาดและไม่บันทึกทั้งชุด
- ผลนำเข้าแสดงจำนวนเพิ่มใหม่ เขียนทับ และข้ามรายการในประวัติ ยังคงจำกัดสิทธิ์นำเข้าเฉพาะ Admin ขณะเปิดระบบ

หากนำเข้าด้วย CSV และมีชื่อครูหลายคน ให้ครอบค่าทั้งช่องครูผู้สอนด้วยเครื่องหมายคำพูดคู่ เพราะภายในช่องมีจุลภาคคั่นชื่อ

ส่งออก CSV UTF-8 BOM เปิดใน Excel ได้ ใส่ apostrophe ก่อนค่าเสี่ยงเป็นสูตร รายงานสำเร็จมีเกรดใหม่และเวลาที่ฝ่ายวิชาการอนุมัติ

## ความปลอดภัยและการใช้งานจริง

- RLS ควบคุมข้อมูลตามเจ้าของและบทบาท ไม่มีสิทธิ์ insert/update/delete ตารางโดยตรงผ่าน client
- ไฟล์มอบหมายเก็บใน Supabase Storage bucket แบบ private ใช้ signed URL อายุ 10 นาที และ policy จำกัดเฉพาะนักเรียนเจ้าของรายการ ครูเจ้าของวิชา และฝ่ายวิชาการ
- เปลี่ยนสถานะผ่าน PostgreSQL RPC เท่านั้น ตรวจบทบาท เจ้าของ สถานะเดิม เวลาระบบ และล็อกแถวป้องกันการอนุมัติซ้ำพร้อมกัน
- ไม่มีสิทธิ์แก้บทบาทตนเอง บัญชีสร้างด้วย service role เฉพาะเครื่องมือ offline
- Auth cookies เป็น HttpOnly, SameSite=Lax, Secure ใน production; Next.js server actions ตรวจ origin โดย framework
- ปิด indexing, ไม่ cache หน้าใช้งาน, มี security headers, ไม่ใช้ `dangerouslySetInnerHTML`
- Audit log สำหรับทุก transition/import/การตั้งเวลา ไม่มีเลขบัตรประชาชน ไม่มี public registration
- Web Push เก็บ endpoint แยกตามครูและอุปกรณ์ ใช้ service role เฉพาะฝั่ง server เพื่อนำส่ง และลบ endpoint ที่หมดอายุเมื่อบริการ Push ตอบกลับว่าใช้ไม่ได้
- `/demo` ใช้ข้อมูลสมมติแยกจากฐานข้อมูล เปลี่ยนแปลงในหน่วยความจำเท่านั้น รีเฟรชจะรีเซ็ต ไม่ใช้ทดแทนการทดสอบฐานข้อมูลจริง
- ต้องทดสอบบัญชีจริงครบสี่บทบาทด้วย staging, เปิด backup/PITR ตามแผน Supabase, ตั้ง monitoring, จำกัดผู้ถือ service role และทบทวนนโยบายข้อมูลก่อนเปิดบริการ

Web Push ต้องใช้ HTTPS ใน production ครูต้องอนุญาตการแจ้งเตือนในเบราว์เซอร์ ส่วน iPhone/iPad ต้องเพิ่มเว็บไซต์ไว้ที่หน้าจอโฮมก่อนจึงเปิดรับ Web Push ได้

## ตรวจสอบ

### สไตล์และ Tailwind CSS

ใช้ Tailwind CSS v4 ผ่าน `@tailwindcss/postcss` สำหรับสไตล์ทุกหน้า รวมถึง responsive, focus, disabled และแถบความคืบหน้า ไม่มี CSS component แบบเดิมหรือ inline style ในโค้ดแอป

- `src/app/globals.css` มีเฉพาะการนำเข้า Tailwind และ `@theme` สำหรับสี ฟอนต์ และ breakpoint
- คลาส Tailwind อยู่ใน `className` ของแต่ละ element โดยตรง ไม่มีไฟล์หรือตัวแปรแยกเก็บชุดสไตล์
- สถานะที่เปลี่ยนตามข้อมูลใช้เงื่อนไขภายใน `className` และ `twMerge()` จาก `tailwind-merge` จัดการคลาสที่ทับกัน
- ใช้ชื่อคลาสแบบเต็มในแต่ละสถานะ เพื่อให้ Tailwind ตรวจพบตอน build; ฟอนต์ไทยโหลดจาก `@fontsource-variable/noto-sans-thai`

### คำสั่งตรวจสอบ

`npm test` ตรวจ state machine, ตารางเวลา, CSV injection, import validation และ auth identity

`npm run typecheck` และ `npm run build` ตรวจ TypeScript และ production build

`npx tsx scripts/check-connection.ts` ตรวจเชื่อมต่อแบบไม่แสดง key; ไม่มี migration จะขึ้น PGRST205

แนวทาง SSR ตาม [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client) และ [Next.js Proxy](https://nextjs.org/docs/app/getting-started/proxy)

## สิ่งที่ต้องติดตั้งใน Supabase

Publishable key ไม่สามารถสร้างตารางหรือสร้างบัญชีผู้ใช้ได้ จึงต้องรัน SQL และ provision บัญชีโดยผู้มีสิทธิ์โครงการก่อน การมีหน้าเว็บและเชื่อม API ได้ยังไม่ใช่การติดตั้งฐานข้อมูลสำเร็จ

สำหรับการ์ดสถิติจำนวนนักเรียน ให้รัน `supabase/migrations/007_manager_student_counts.sql` หลัง 006 เพื่อรวมจำนวนนักเรียนที่เสร็จสิ้น/ยังไม่เสร็จสิ้นทั้งหมด รวมผู้ที่ไม่มีระดับชั้น ม.1–ม.6 โดยนักเรียนจะเสร็จสิ้นเมื่อฝ่ายวิชาการอนุมัติครบทุกวิชา

สำหรับสรุปจำนวนรายการคงค้างแยกตาม 5 สถานะบนหน้า Dashboard ผู้บริหาร ให้รัน `supabase/migrations/008_manager_outstanding_statuses.sql` หลัง 007 โดยแสดงเฉพาะจำนวนรวมและไม่เปิดเผยข้อมูลนักเรียนรายบุคคล

หน้า “รายชื่อนักเรียนที่ยังไม่เรียบร้อย” และ “รายชื่อนักเรียนที่เรียบร้อยแล้ว” ของผู้บริหารใช้ `supabase/migrations/009_manager_student_lists.sql` (รันหลัง 008) เพื่อค้นหาและแบ่งหน้ารายชื่อโดยนับสถานะนักเรียนจากทุกรายวิชา ฟังก์ชันนี้ตรวจบทบาท manager และส่งกลับเฉพาะเลขประจำตัวนักเรียน ชื่อ ชั้น/ห้อง ปี/ภาคเรียนล่าสุด และจำนวนรายการรายวิชา ไม่ส่งเลขบัตรประชาชนหรือรายละเอียดผลการเรียนรายวิชา

Modal รายละเอียดรายวิชาของนักเรียนใช้ `supabase/migrations/010_manager_student_courses.sql` (รันหลัง 009) เพื่อดึงข้อมูลรายวิชาเมื่อผู้บริหารเปิดดูรายการ ฟังก์ชันตรวจบทบาท manager และส่งเฉพาะปี/ภาคเรียน รหัสและชื่อวิชา หน่วยกิต ครูประจำวิชา ผลการเรียนเดิม และสถานะปัจจุบันของแต่ละวิชา

ตัวกรองระดับชั้น ปีการศึกษา และภาคเรียนในหน้ารายชื่อนักเรียนใช้ `supabase/migrations/011_manager_student_filters.sql` (รันหลัง 010) โดยกรองตามชั้น/ห้องและปี/ภาคเรียนล่าสุดของนักเรียน ยอดสถานะรายวิชายังคงนับจากทุกรายวิชา

ครูร่วมสอนหลายคนใช้ `supabase/migrations/012_multi_teachers.sql` (รันหลัง 011) เพื่อแปลงข้อมูลครูเดิมเป็น array หนึ่งสมาชิก และปรับสิทธิ์รายการ งานแนบ การนำเข้า และการดำเนินสถานะให้ครูทุกคนในรายวิชาเดียวกันใช้งานได้
