เว็บที่ผู้ใช้ยืนยัน: https://mst-grs.vercel.app

## สรุป

ยังไม่พบการข้ามสิทธิ์จาก student/teacher/academic/manager ไปเป็น admin หรือการอ่านผลการเรียนของคนอื่นผ่าน RLS ในกรณีที่ทดสอบ แต่พบช่องโหว่เชิงกระบวนการสมัครครูและจุดเสี่ยงด้านการเรียกเครือข่าย/ใช้ทรัพยากร 3 เรื่องที่ทำซ้ำได้ในเครื่อง

| รหัส | ระดับประเมิน       | สิ่งที่พบ                                                                                       | สถานะหลักฐาน                                                                               |
| ---- | ------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| F1   | สูง                | สมัครเป็นครูโดยไม่มีการยืนยันบุคลากร และนำเข้าเกรดผูกครูด้วยชื่อ                                | ทำซ้ำด้วยข้อมูลจำลอง: บัญชีที่ไม่ผ่านการยืนยันอ่านเกรดที่นำเข้าโดยชื่อตรงกันได้            |
| F2   | ปานกลาง            | Push subscription รับปลายทาง HTTPS ใดก็ได้ ทำให้เซิร์ฟเวอร์เตรียมส่งคำขอไปปลายทางที่ผู้ใช้กำหนด | SQL ยอมรับ loopback และ sender เรียก HTTPS request ด้วยปลายทางนั้น; ดักก่อนส่งเครือข่าย    |

ระดับของ F1–F3 เป็นการประเมินผลกระทบต่อแอปนี้ ไม่ใช่คะแนน CVSS ที่คำนวณอย่างเป็นทางการ รายงานนี้ไม่ได้รับรองว่าเว็บไม่มีช่องโหว่อื่น และไม่ได้อ้างว่าขโมยข้อมูลหรือรันโค้ดบนเซิร์ฟเวอร์จริงได้

## สิ่งที่ทดสอบและผล

- ชุดทดสอบเดิม: **90 ผ่าน, 0 ล้มเหลว** รวม role/session, ประวัติเกรด, การอนุมัติ, อัปโหลด, นำเข้า, การจัดการบัญชี และการยกเลิกงานนำเข้า
- ชุดจำลองโจมตีเพิ่มเติม: **351 จุด** — 310 คำขอถูกปฏิเสธ/ป้องกัน, 28 การอ่านข้อมูลได้เฉพาะขอบเขต, 10 การตรวจอื่นผ่าน และ 3 จุดอ่อนทำซ้ำได้ ตัวเลขนี้ไม่ใช่ 351 ช่องโหว่หรือ 351 รูปแบบโจมตีที่ไม่ซ้ำกัน
- ตรวจ inventory ของฐานข้อมูลจำลอง: 15 public tables, 48 functions, 19 RLS policies; public tables ทั้งหมดเปิด RLS
- เว็บจริง: 28 HTTP probes รวมหน้าเว็บ, API, browser chunks และตัวอย่าง source map
- Supabase ที่ตั้งค่าในเครื่อง: 18 anonymous read probes ถูกปฏิเสธทั้งหมด ใช้เฉพาะ public key
- เบราว์เซอร์ Edge บนเว็บจริง: 6 การตรวจ redirect, reflected XSS ผ่าน query string, external return URL และหน้าสมัครครู
- TypeScript: `tsc --noEmit` ผ่าน

### การข้าม role และการเข้าถึงข้อมูล

ทดสอบด้วยนักเรียน 2 คน ครู 2 คน ฝ่ายวิชาการ ผู้บริหาร และผู้ดูแลระบบ พร้อม session แยกกัน:

| ผู้เรียก    | ผลการอ่านตารางเกรด/งาน/ไฟล์ในชุดจำลอง                                 |
| ----------- | --------------------------------------------------------------------- |
| ไม่ล็อกอิน  | ไม่มีสิทธิ์อ่าน public tables                                         |
| นักเรียน    | อ่านได้เฉพาะรายการของตน                                               |
| ครู         | อ่านได้เฉพาะรายการที่มี ID ตนในผู้สอน                                 |
| ฝ่ายวิชาการ | อ่านได้ทั้งสองรายการ ตามสิทธิ์งานวิชาการ                              |
| ผู้บริหาร   | อ่านตารางเกรดโดยตรงไม่ได้; ใช้ RPC สถิติและรายละเอียดตามที่ระบบอนุญาต |
| Admin       | อ่านตารางเกรดโดยตรงไม่ได้; ใช้ RPC จัดการระบบตามสิทธิ์                |

ตรวจเพิ่มเติมแล้ว:

- เปลี่ยน `profiles.role`, แก้ตารางเกรดตรง ๆ หรือลบ audit/history ด้วย authenticated role ไม่ได้
- เรียก RPC ของ Admin จาก role อื่นไม่ได้ รวมรายชื่อ, เพิ่ม/แก้ไข/ลบบัญชี, รีเซ็ตบัญชี, จบการศึกษา, นำเข้าและตั้งเวลา
- เรียก RPC ของ Manager จาก role อื่นไม่ได้
- เรียก service-only RPC เพื่อเพิ่ม role หรือ activate session เองไม่ได้
- ใส่ `role=admin` ใน JWT metadata จำลองไม่เปลี่ยนสิทธิ์ที่ `my_role()` คืนมา
- ใช้ session ID ของบัญชีอื่น หรือ session ที่ถูกลบแล้ว ไม่ได้สิทธิ์อ่านเกรด
- นักเรียนขอแก้เกรดของคนอื่นไม่ได้ และครูแก้เกรดที่ไม่ใช่ของตนไม่ได้ในกรณีที่ทดสอบ
- อัปโหลดไปพื้นที่งานที่ไม่มีสิทธิ์ไม่ได้ และลบไฟล์ที่ผูกกับงานแล้วผ่าน cleanup ไม่ได้
- คำค้น SQL injection เช่น `' OR 1=1 --` ถูกประมวลผลเป็นข้อความค้นหา ไม่กลายเป็น SQL
- ชุดทดสอบเดิมตรวจ isolation ของข้อมูลย้อนหลัง/ไฟล์ย้อนหลัง การแก้ไขที่ข้อมูลเปลี่ยนไปแล้ว การอนุมัติสองขั้น และ rollback เมื่อ import ผิดพลาด

การใส่ JWT claims ในฐานข้อมูลจำลองเป็นการตรวจตรรกะสิทธิ์หลังยืนยัน JWT เท่านั้น ไม่ใช่การพิสูจน์ว่าสามารถปลอมลายเซ็น JWT ของ Supabase ได้

### ผลตรวจเว็บจริง

- `/dashboard`, `/dashboard/admin`, `/dashboard/manager` และหน้ารายละเอียดงานของ anonymous ถูกส่งกลับหน้าเข้าสู่ระบบ ยืนยันทั้ง streamed redirect และเบราว์เซอร์จริง แม้ HTTP ของหน้า streaming จะเป็น 200
- ส่ง `x-middleware-subrequest`, `RSC: 1` หรือ cookie ปลอม `role=admin; isAdmin=true` แล้วยังถูกส่งกลับหน้าเข้าสู่ระบบ
- API import-control: GET ได้ 405, POST จาก origin เว็บโดยไม่ล็อกอินได้ 401, POST จาก origin อื่นได้ 403 ไม่มีงานนำเข้าถูกสร้าง
- `/.env`, `/.env.local`, `/.git/config`, `/package.json` ได้ 404; source map ตัวอย่างได้ 403
- ไม่พบค่าของ service role key, HMAC secret หรือ VAPID private key ที่ตั้งค่าในเครื่องใน response/chunks ที่ตรวจ ไม่ได้พิสูจน์ว่าค่าลับทุกตัวของ deployment ไม่เคยรั่ว
- มี HSTS, `nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, Referrer/Permissions Policy และ private/no-store caching
- payload SVG event handler ใน `role`/`next` ไม่ทำงานในเบราว์เซอร์; external `next` ไม่พาออกนอก origin ก่อนล็อกอิน การจำกัดปลายทางหลังล็อกอินมี unit test แยก

## F1 — สมัครเป็นครูและผูกข้อมูลด้วยชื่อที่ผู้สมัครกำหนดเอง

ตำแหน่ง:

- `src/app/register/actions.ts:24` และ `:82` — public Server Action สร้าง Auth user และยืนยัน email ภายในทันที
- `src/lib/auth-input.ts:3` — ตรวจเลขบัตรเพียงรูปแบบ 13 หลัก
- `supabase/migrations/029_teacher_registration.sql:24` — สร้าง profile เป็น teacher ทันที
- `supabase/migrations/031_multi_role_login.sql:221` — นำเข้าเกรดเลือกครูจาก `full_name`

**เงื่อนไขโจมตี:** ผู้สมัครเลือกชื่อครูที่ยังไม่มีบัญชีชื่อนั้น เมื่อ Admin นำเข้าไฟล์ที่ระบุชื่อเดียวกัน ระบบจะพบครูเพียงหนึ่งบัญชีและผูกเกรดเข้ากับผู้สมัครรายนั้น ไม่มีขั้นอนุมัติหรือรายชื่อบุคลากรที่ตรวจสอบแล้วมาคั่น

**หลักฐาน:** สคริปต์ใช้ข้อมูลสมมติ รวมเลข `0000000000000` ซึ่งผ่าน schema เรียก `provisionTeacher` ด้วย Auth adapter จำลองและ SQL จริงจาก migrations จากนั้นเปิด session, จำลอง Admin นำเข้าเกรดหนึ่งรายการ และบัญชีครูที่สมัครเองอ่านรายการนั้นได้ ชุดทดสอบไม่ได้สมัครบัญชีบน production

นี่ไม่ใช่การยึดบัญชีครูเดิม และไม่ทำให้เห็นเกรดทุกคนทันที ต้องมีการนำเข้าที่ใช้ชื่อตรงกัน หากมีบัญชีชื่อเดียวกันอยู่แล้ว ระบบจะปฏิเสธการจับคู่เพราะชื่อซ้ำ ซึ่งยังอาจใช้ก่อกวนการนำเข้าได้

**แนวทางแก้:** ใช้คำเชิญหรือให้ Admin อนุมัติก่อนให้ teacher role ที่มีสิทธิ์ทำงาน และนำเข้าด้วยรหัสบุคลากร/ID ที่ตรวจสอบแล้ว เพิ่มหน้าตรวจสอบการจับคู่ครูก่อนยืนยันนำเข้า การตรวจ checksum เลขบัตรเพียงอย่างเดียวไม่ยืนยันว่าผู้สมัครเป็นเจ้าของเลขหรือเป็นครูจริง

## F2 — ปลายทาง Push เปิดทางให้ส่ง HTTPS ไปยังที่อยู่ที่ผู้ใช้เลือก

ตำแหน่ง:

- `supabase/migrations/003_web_push.sql:34` — ตรวจเพียงขึ้นต้น `https://`
- `src/app/actions.ts:80` — schema ไม่มีข้อจำกัด host/port
- `src/lib/push.ts:74` — ส่งทุก subscription ด้วย `Promise.all` และ `webpush.sendNotification`

**หลักฐาน:** ครูจำลองบันทึก endpoint `https://127.0.0.1:9443/audit-only` พร้อม encryption keys ที่ถูกต้องได้ จากนั้น `web-push` ที่ติดตั้งจริงเรียก `https.request` ด้วย hostname `127.0.0.1` และ port `9443` สคริปต์ดัก request แล้วหยุดก่อนส่งเครือข่าย

**ผลกระทบและข้อจำกัด:** เป็นเส้นทาง SSRF แบบ blind HTTPS POST เมื่อเปิด Push และมีนักเรียนยื่นคำร้องให้ครูนั้น ปลายทางภายในอาจได้รับการเชื่อมต่อหรือทำให้การส่งค้าง ทั้งนี้ยังขึ้นกับ TLS certificate และข้อจำกัด egress ของโฮสต์ ไม่ได้พิสูจน์ว่าอ่าน response ภายใน ดึง secrets หรือโจมตี metadata service ได้ Payload ที่ส่งเป็นข้อความ Push เข้ารหัส ไม่ใช่ HTTP body ที่เลือกได้อย่างอิสระ

**แนวทางแก้:** จำกัด endpoint ให้เป็นผู้ให้บริการ Web Push ที่รองรับ ตรวจ URL/port และ IP ที่ resolve ได้ ปฏิเสธ loopback/private/link-local เพิ่ม timeout, จำกัดจำนวน subscriptions ต่อบัญชี และจำกัดจำนวนการส่งพร้อมกัน ตรวจทั้งตอนบันทึกและก่อนส่ง รวมถึงล้าง endpoint เก่าที่ไม่ผ่านกติกา

## F3 — anonymous สร้างข้อมูล rate-limit ด้วย bucket ใดก็ได้

ตำแหน่ง: `supabase/migrations/001_initial.sql:115` และ `:127`

`consume_login_attempt(text)` เป็น SECURITY DEFINER ที่ให้ anon/authenticated เรียกได้ และรับค่า hex 64 ตัวจากผู้เรียกโดยตรง ทุกคำขอสามารถเพิ่ม bucket ใหม่และเรียก cleanup ของตารางได้

**หลักฐาน:** bucket เดียวผ่าน 10 ครั้งและถูกจำกัดครั้งที่ 11 แต่เปลี่ยนเป็น 12 buckets ใหม่แล้วผ่านครบ เกิด 13 rows จาก 23 คำขอในเครื่อง ไม่มีการยิงจำนวนมากบนเว็บจริง

**ผลกระทบ:** เปิดช่องใช้ทรัพยากร DB/พื้นที่เก็บข้อมูลโดยไม่ต้องล็อกอิน การสร้าง bucket ใหม่จำนวนมากทำให้ตารางโต และ cleanup ซ้ำทุกคำขออาจเพิ่มภาระ ยังไม่ได้ทำ load test เพื่อวัดจุดล่มหรือประสิทธิภาพ production

**ไม่ใช่หลักฐานว่าข้ามการจำกัดล็อกอินบัญชีจริงได้:** Server Action สร้าง bucket ของบัญชีจริงด้วย HMAC ฝั่งเซิร์ฟเวอร์ ผู้โจมตีเลือก bucket ของ Server Action ไม่ได้

**แนวทางแก้:** ย้ายการเรียก limiter ไปใช้ service client ฝั่งเซิร์ฟเวอร์ แล้ว revoke EXECUTE จาก anon/authenticated พร้อมเพิ่ม source/global limits ที่เชื่อถือได้ ทำ cleanup เป็นงานตามเวลาและประเมิน index `window_start`/ขนาดข้อมูล

## D1 — Dependency advisory ของ Next.js

`npm audit` พบ 1 Critical advisory ใน Next.js ที่ติดตั้ง **16.3.5**: `GHSA-vcvr-r3jv-pc5j` / `CVE-2026-94545` รุ่นแก้ไขเริ่มที่ **16.3.6**

ประกาศผู้พัฒนาระบุว่าเกี่ยวกับ Node.js `ImageResponse` จาก `next/og` ที่รับค่าซึ่งผู้โจมตีควบคุมเข้า SVG content/attributes/styles การค้นใน `src` ไม่พบการใช้ `ImageResponse` หรือ `next/og` จึงจัดเป็น dependency ที่ควรอัปเดต ไม่ใช่ช่อง RCE ที่พิสูจน์ได้ในเว็บนี้ รุ่นบน deployment ยังไม่ได้ยืนยันกับ build ในเครื่อง

แหล่งข้อมูล: [ประกาศความปลอดภัยของ Next.js](https://github.com/vercel/next.js/security/advisories/GHSA-vcvr-r3jv-pc5j)

## ข้อเสนอเสริมจากการอ่านโค้ด

รายการต่อไปนี้แยกจากสามจุดที่ทำซ้ำได้:

1. **บัญชีนักเรียนใช้เลขบัตรเป็นข้อมูลเข้าสู่ระบบ:** `src/lib/auth-input.ts:19`, `src/lib/identity.ts:20` ผู้ที่รู้รหัสนักเรียนและเลขบัตรสามารถเข้าสู่ระบบด้วย flow ปกติ HMAC ช่วยปกป้องค่าที่เก็บกับ Auth แต่ไม่ได้เพิ่มหลักฐานว่าเป็นเจ้าของบัญชี ควรใช้รหัสผ่านเฉพาะบุคคลและเปลี่ยนเมื่อเข้าใช้ครั้งแรก
2. **รหัสผ่านบุคลากรขั้นต่ำ 6 ตัวและไม่มี MFA enforcement ในแอป:** พิจารณายกระดับรหัสผ่านและ MFA สำหรับ Admin/ฝ่ายวิชาการ/Manager โดยตรวจความเข้ากันได้กับนโยบาย Supabase จริงด้วย
3. **CSP อนุญาต inline scripts:** `next.config.ts:31` และ response จริงมี `script-src 'unsafe-inline'` ทำให้ CSP ช่วยหยุด XSS ได้น้อยลง ควรประเมิน nonce/hash ให้เข้ากับ Next.js ไม่ได้พบ XSS ที่ทำงานจากการทดสอบครั้งนี้
4. **ไม่มี quota อัปโหลดในระดับแอป:** migration 019 ยกเลิก bucket file size limit และโค้ดไม่จำกัดจำนวน/ขนาดรวม สอดคล้องกับความสามารถรับไฟล์ใหญ่ที่มีอยู่ แต่ควรมี quota ต่อครู/ต่องานและติดตามค่าใช้จ่าย ตรวจ global Storage limit ของ production แยก ไม่ได้ทดลองเติม Storage จริง
5. **ชนิดไฟล์ตรวจจาก extension และ Storage MIME metadata:** ไม่ใช่การสแกนเนื้อหา/มัลแวร์ ควรพิจารณาการสแกนไฟล์แนบก่อนเปิดให้นักเรียนดาวน์โหลด โดยเฉพาะเอกสาร Office

## ขอบเขตที่ยังไม่ยืนยัน

- ไม่มีบัญชีทดสอบจริงแต่ละ role จึงยังไม่ได้ทดสอบ authenticated browser → Server Action → Supabase ครบทุก flow บน deployment
- DB จำลองใช้ PGlite และ Auth/Storage schema แบบจำลอง ไม่จำลองการตรวจลายเซ็น JWT, GoTrue, signed-upload transport, Storage global quota หรือ pg_cron
- ทดสอบ Supabase anonymous ด้วย URL/public key ที่ตั้งค่าในเครื่อง แต่ไม่พบ URL ดังกล่าวใน public responses จึงยังไม่ยืนยันว่าเป็น project เดียวกับ deployment ที่ระบุ
- ไม่ได้ตรวจ Supabase dashboard settings, Vercel permissions/WAF, MFA settings, production schema drift, backup/restore, การหมุน secrets หรือประวัติการรั่วทั้งหมดใน Git
- ไม่ได้ทดสอบ DoS, เดารหัสผ่านจำนวนมาก, ส่ง malware, ทำ SSRF จริง หรือแก้ไข/ลบข้อมูลจริง
- ไม่ได้สร้างบัญชีจริงหรือเปลี่ยน migrations/dependencies/พฤติกรรมแอปในงานตรวจครั้งนี้

การตรวจ authenticated production ให้ครบต้องมีบัญชีทดสอบที่ยืนยันแล้วสำหรับแต่ละ role และข้อมูลที่อนุญาตให้ทดสอบ หรือ staging ที่ใช้ config และ migrations เดียวกับ production

## ลำดับแก้ไขที่เสนอ

1. ปิดช่องสมัครครูที่ไม่ผ่านการอนุมัติ และทบทวนบัญชีครูที่มีอยู่กับรายชื่อบุคลากรจริง
2. จำกัดปลายทาง Push และทำ rate-limit RPC ให้เรียกได้จากเซิร์ฟเวอร์เท่านั้น
3. อัปเดต Next.js เป็นรุ่น patched พร้อม typecheck/test/build ก่อน deploy
4. ยกระดับการเข้าสู่ระบบ, CSP และ quota/การสแกนไฟล์ตามการใช้งานของโรงเรียน
5. ทดสอบซ้ำด้วยบัญชีจริงสำหรับทดสอบแต่ละ role หลังแก้ไข โดยเก็บกรณีโจมตีเป็น regression tests

## ไฟล์และการทดสอบซ้ำ

สคริปต์ที่เพิ่ม:

- `scripts/security-local-audit.ts` — ใช้ฐานข้อมูลชั่วคราวในเครื่องเท่านั้น; จุด F1–F3 เป็น assertions ที่ยืนยันพฤติกรรมช่องโหว่ปัจจุบัน เมื่อแก้แล้วต้องปรับเป็นการคาดหวังให้ปฏิเสธ
